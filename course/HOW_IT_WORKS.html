Postgres — the bank's live system

Postgres plays the bank's core system: customers, accounts, transactions, cards. It runs in Docker as meridian_postgres on port 5432. It is the source: we only read from it, never write analytics back into it.

Schemasref (currencies, FX, products, merchants), core (customers, accounts, transactions, cards), cdc (the delete log).
Seed data200k customers and 5M transactions so performance is real, not toy.
Simulatorsim_tick() posts 500 transactions, settles some, reverses some, and hard-deletes one row, so every CDC case happens.

The two triggers that make change capture possible

01_source_postgres/04_cdc_triggers.sql

-- 1. Every UPDATE bumps updated_at. Apps forget; the trigger doesn't.
NEW.updated_at := clock_timestamp();     -- not now(): now() is frozen for the whole transaction

-- 2. Every DELETE leaves a note, because a deleted row can't be "selected" later.
INSERT INTO cdc.deleted_records (schema_name, table_name, pk_value, deleted_at)
VALUES (TG_TABLE_SCHEMA, TG_TABLE_NAME, v_pk, clock_timestamp());
sequenceDiagram participant App as Bank app / simulator participant T as transactions table participant Trg as triggers participant D as cdc.deleted_records App->>T: INSERT txn 101 (PENDING) Trg-->>T: updated_at = 10:00:00 App->>T: UPDATE txn 101 -> POSTED Trg-->>T: updated_at = 10:04:00 App->>T: DELETE txn 77 Trg->>D: (core, transactions, 77, 10:05)
The updated_at column is a "last touched" sticker on every file in a cabinet. The delete log is a sign-out sheet: when a file is shredded, someone writes its number on the sheet, so head office finds out.
We read changes by timestamp, so the source has to promise two things: every change moves the timestamp, and every delete is written down. These two triggers are that promise.
The Postgres count kept climbing. The simulator is a while True loop, 500 rows every 5 seconds, until you press Ctrl+C. A live source never stands still, so you compare counts as of a point in time, never "right now".

Python — the courier (extract and load)

Why Python and not dbt? dbt can only transform data already inside Snowflake. It cannot reach your laptop's Postgres. Moving bytes from one system to another is extract and load. That is Python's job here, and in companies it's often Fivetran, Airbyte or Debezium.

02_ingestion_python/pg_to_snowflake.py — five steps per table

flowchart TD A["1. Read bookmark\nSELECT last_watermark FROM CONTROL.WATERMARKS"] --> B["2. Pick a safe window\nlow = bookmark\nhigh = now - 10 s lag"] B --> C["3. Extract\nSELECT * WHERE updated_at > low AND updated_at <= high\n(server-side cursor, 200k rows per chunk)"] C --> D["4. Write Parquet files\n/tmp/meridian_ingest/*.parquet"] D --> E["5a. PUT files to Snowflake stage\n5b. COPY INTO raw table (VARIANT)"] E --> F{"COPY succeeded?"} F -->|yes| G["Move bookmark to the max updated_at actually seen\nwrite LOAD_LOG row = SUCCESS"] F -->|no| H["Bookmark NOT moved\nLOAD_LOG = FAILED\nnext run retries the same window"]

The idea in one picture: the watermark

time  ──────────────────────────────────────────────────────────►
       already loaded       │  this run's window     │ lag │ now
       ████████████████████ │ ░░░░░░░░░░░░░░░░░░░░░░ │ 10s │
                         bookmark                  high
Why a 10-second lag?A transaction that started at 09:59:59 might commit after we read. Stopping 10 s short of now gives slow commits time to land, so we don't skip them.
Why move to "max seen", not "high"?If a quiet table had no rows, we keep the old bookmark. A row that arrives late with an older timestamp can still be caught.
Why Parquet?Typed (a decimal stays a decimal), compressed, and Snowflake loads it in parallel. CSV loses types and breaks on commas.
Why idempotent?If anything fails, the bookmark doesn't move. Running again produces the same result. Raw might get a duplicate copy, and dbt removes it later.

The load itself

PUT file:///tmp/meridian_ingest/transactions_<batch>_*.parquet @stage AUTO_COMPRESS=FALSE PARALLEL=8

COPY INTO MERIDIAN_RAW.POSTGRES_CORE.TRANSACTIONS (record, _extracted_at, _batch_id, _source_file)
FROM (SELECT $1, '<extracted_at>', '<batch>', METADATA$FILENAME FROM @stage)
ON_ERROR = ABORT_STATEMENT     -- never load half a batch
PURGE = TRUE                   -- delete the files once loaded
The watermark is a bookmark in a novel that is still being written. Each visit you read from the bookmark to the last finished page (not the one the author is typing), then move the bookmark to the last page you actually read.
The loader is boring on purpose. It reads what changed since its bookmark, ships it as Parquet, and only moves the bookmark after Snowflake confirms the load. If it crashes, rerunning it is safe.
zsh: command not found: python. On a Mac there's no python until the project's .venv is activated, and scripts must be run from the project folder. The environment is part of the system, so it must be part of the instructions.

flowchart LR subgraph Postgres["Postgres: current state"] P1["txn 101 · POSTED"] end subgraph Raw["Snowflake raw: every version"] R1["txn 101 · PENDING · batch A"] R2["txn 101 · POSTED · batch B"] R3["txn 77 · deleted in Postgres, still here"] end P1 -. loaded twice .-> R1 & R2
Raw is a photocopy of every version of every receipt. If the till changes a receipt, you get a second photocopy. Shredding the original doesn't shred the copies.
Raw is append-only. It's our evidence. If dbt has a bug, we fix it and rebuild from raw. We never have to go back to the bank's live system.
Snowflake raw had more rows (5,310,771) than Postgres (5,309,358). That is correct, not a bug. Raw counts every version, plus rows later deleted. Only after dbt deduplicates does the count match Postgres.
A view failed with unexpected 'rows'. ROWS is a reserved word in Snowflake, so AS rows became AS rows_loaded. Lesson: name columns for what they mean.

dbt — the kitchen (transform inside Snowflake)

dbt is SQL files plus a compiler. Each .sql file is one table or view. {{ ref('x') }} tells dbt "this depends on x", so dbt knows the build order and draws the lineage graph. dbt itself moves no data. It sends SQL to Snowflake, and Snowflake does the work.

flowchart LR subgraph Bronze["Bronze = RAW"] r[(raw VARIANT\n22 sources)] end subgraph Silver["Silver = STAGING + INTERMEDIATE"] s["21 staging models\nparse JSON, rename, dedupe"] snap["3 snapshots\nSCD2 history"] i["3 intermediate\nFX per day, primary holder"] end subgraph Gold["Gold = MARTS"] d["dimensions\ndim_customer, dim_account, dim_branch..."] f["facts\nfct_transactions, fct_card_authorizations..."] x["serving\nomni_search, ml_customer_features, offers"] end r --> s --> i --> f s --> snap --> d --> f f --> x

The folders use Kimball names (staging, marts) rather than bronze/silver/gold because the gold layer is a star schema (ADR 0003). It's the same idea under a different label.

4.1 Staging: keep the newest version

models/staging/postgres/stg_postgres__transactions.sql

select record:transaction_id::number as transaction_id,
       record:status::string         as status,
       record:updated_at::timestamp_ntz as updated_at, ...
from {{ source('postgres_core', 'transactions') }}
qualify row_number() over (partition by transaction_id
                           order by updated_at desc, _extracted_at desc) = 1
Ten photocopies of receipt 101. Line them up by "last touched", keep the top one, bin the rest.

This exact rule is proved by a unit test: fake input of PENDING then POSTED, expected output of one POSTED row.

A MERGE can update and insert, but it can never delete a row it doesn't see. That's why deletes need a separate step that reads the Postgres delete log.

4.5 Dev vs prod

--target dev builds into DBT_FK_* schemas with only the last 30 days of data, which is cheap and safe. --target prod builds the real MERIDIAN_ANALYTICS.MARTS. That's why reconcile failed before the prod build: the table it reads didn't exist yet.

The unit test returned nothing. limit_in_dev added a 30-day filter, and the fixture was dated 2026-09-01, more than 30 days earlier. Fix: never apply the dev filter inside unit tests. Lesson: helper macros apply to tests too.
"dbt was unable to infer all dependencies". The delete hook called ref() only on incremental runs, so dbt never saw the dependency when it parsed the project. Fix: -- depends_on: {{ ref('stg_postgres__deleted_records') }} at the top of the model.
Contract failure: TIMESTAMP_LTZ vs TIMESTAMP_NTZ. current_timestamp() returns a timestamp with time zone. The contract promised one without, so it was cast with ::timestamp_ntz. This is exactly the drift contracts exist to catch.

Airflow — the alarm clock and the foreman

Airflow transforms nothing. It decides when each step runs, in what order, how many at once, what to retry, and who to alert. Every task is a shell command you already ran by hand.

flowchart LR subgraph M["meridian_microbatch_ingest · every 5 min"] direction LR e1["extract_load\ntransactions"] & e2["extract_load\naccounts"] & e3["extract_load\ncard_authorizations"] & e4["extract_load\ndeleted_records"] --> b["dbt build\n--selector microbatch"] --> h["assert_pipeline_health\n(fail if > 15 min stale)"] end subgraph D["meridian_daily_batch · 02:00 UTC"] direction LR x["extract_daily\n17 slow tables"] --> s["dbt snapshot\n(SCD2)"] --> bd["dbt build\n(everything)"] --> rc["reconcile\nPostgres vs Snowflake"] --> dc["dbt docs"] --> mf["save prod manifest"] end
Pool meridian_postgres = 4 slotsAt most 4 extracts hit Postgres at once, so the bank's app isn't starved.
max_active_runs=1A slow run never overlaps the next one. Two loaders racing on one bookmark would corrupt it.
catchup=FalseThe bookmark already knows where we are. Replaying old 5-minute slots is meaningless.
Two cadencesHot tables every 5 minutes. SCD2 snapshots daily, because running them every 5 minutes would create pointless versions.
Airflow is a foreman with a clipboard. "Four drivers, go. When all four are back, cook. When cooking is done, check the temperature. If anyone fails, retry twice, then shout."
The daily DAG sat "running" for 17 minutes doing nothing. Its tasks asked for pool meridian_postgres, which didn't exist, so the scheduler logged "non-existent pool" forever. Fix: create the pool (astro dev object import). Lesson: "running" doesn't mean working. Read the scheduler log.
Reconcile failed on the oldest day only: Postgres 484 rows, Snowflake 1,107. Postgres used "the last 7×24 hours" and Snowflake used "7 whole dates", so the first day was only partly counted on one side. Fix: create one cutoff in Python, pass the same cutoff to both systems, and compare the same whole UTC dates. Lesson: a reconciliation is only as good as its window definition.

Governance — same question, different rows

A row access policy is a function Snowflake attaches to a table. Every query, from any tool (worksheet, app, BI), passes each row through it. If the result is FALSE, the row doesn't exist for that user.

flowchart TD Q["SELECT count(*) FROM fct_card_authorizations"] --> P{"RAP_CUSTOMER_SCOPE(customer_id)\nwho is CURRENT_USER()?"} P -->|MERIDIAN_CEO| A["every row"] P -->|MERIDIAN_BM_MUMBAI| B["customers whose home branch is Mumbai"] P -->|MERIDIAN_STAFF_MUMBAI| C["same rows as manager,\nemail/phone masked '***'"] P -->|MERIDIAN_CUSTOMER| E["only their own rows"] P -->|anyone else| F["nothing"]

Run the query as each user and write your real counts here. The order should be: CEO, then manager and staff (equal), then customer.

Security owns the rules03_snowflake/06_row_level_security.sql creates the policies and the APP_USER table (user → persona, branch, customer).
dbt only attaches themEach model declares its policy in meta.governance. A post-hook re-attaches it after every rebuild.
User, not roleInside Streamlit-in-Snowflake every viewer runs as the app's role. Only CURRENT_USER() tells people apart.
Same library, same catalogue, different library cards. The librarian (the policy) checks your card at the shelf, not at the front desk. So sneaking in through a side door (a worksheet instead of the app) doesn't help.
"Unsupported subquery type … inside ROW ACCESS POLICY". The policy used a JOIN, and Snowflake only allows simple lookups in a policy body. It was rewritten as separate EXISTS checks plus one scalar lookup of the manager's branch.

Ask in English — the semantic view and the app

A chat model that only sees 40 table names will eventually guess wrong. It might sum balances across months or join the wrong customer version, and it will sound confident doing it. The semantic view SV_MERIDIAN_BANK is the contract: the allowed tables, the joins, named metrics, business rules, and 4 questions whose SQL a human has checked.

sequenceDiagram actor U as MERIDIAN_CEO participant S as streamlit_app.py participant C as Cortex Analyst participant V as SV_MERIDIAN_BANK participant W as Snowflake warehouse participant R as Row policy U->>S: "How many suspected fraud authorizations?" S->>C: question + semantic_view C->>V: read tables, metrics, rules, verified queries C-->>S: SQL: SELECT COUNT(*) ... WHERE is_rule_suspect S->>W: run that SQL as the logged-in user W->>R: each row: may this user see it? R-->>W: keep / drop W-->>S: result table S-->>U: answer + "SQL the semantic view produced"
The model writes SQL, not answersThe number always comes from Snowflake, never from the language model's memory.
The SQL is shownAnyone can check it. That's how you earn a finance team's trust.
Security isn't in the promptThe rules say "do not add filters to imitate security". The policy does it, so the AI can't talk its way past it.
The AI only translates English into SQL against a contract we wrote. The warehouse computes the number, and the row policy decides what the person may see. Take the AI away and the security still holds.

Test yourself: can you teach it?

Answer out loud before you open each one. If you can do all 12 without peeking, you can teach this.

1. Why can't dbt pull data from Postgres?dbt only sends SQL to the warehouse it's connected to. Postgres is a different system on your laptop. Moving data between systems is extract and load, done here by pg_to_snowflake.py.
2. What two things must the source guarantee for watermark CDC?updated_at changes on every update (trigger), and every hard delete is recorded (cdc.deleted_records).
3. Why does the loader stop 10 seconds before "now"?A transaction that hasn't committed yet could later appear with an older timestamp. The lag gives it time to commit before we read past it.
4. The loader crashes halfway. What happens on the next run?The watermark was never advanced, so it re-reads the same window. Raw may get duplicate copies, and staging's QUALIFY row_number() keeps one.
5. Why does raw have more rows than Postgres?Raw is append-only. It keeps every version of an updated row and rows deleted in Postgres. Postgres keeps only the current state.
6. What does is_incremental() change?On the first run, the model builds the whole table. On later runs, it reads only rows newer than the last _extracted_at (minus a lookback) and MERGEs them on the key.
7. Why a separate hard-delete post-hook?A MERGE can't delete rows absent from its input. The hook deletes ids listed in the delete log.
8. What is fan-out and which test catches it?Joining a fact to an SCD2 dimension without the date-range condition matches every version and multiplies rows. assert_fct_transactions_reconciles_to_staging compares row counts and amounts.
9. Why is the daily snapshot not in the 5-minute DAG?Snapshots create a new history version per detected change. Running every 5 minutes multiplies versions and costs credits for nothing.
10. What does the Airflow pool protect?The bank's live Postgres. At most 4 extracts read from it at the same time.
11. Why CURRENT_USER() and not CURRENT_ROLE() in the policy?In Streamlit-in-Snowflake every viewer runs under the app owner's role. Only the user tells them apart.
12. Where does the number in the chat answer come from?From Snowflake running the generated SQL as the logged-in user, through the row policy. The language model only wrote the SQL.
