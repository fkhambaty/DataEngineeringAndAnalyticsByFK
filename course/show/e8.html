06_predicate_antipatterns.sql

A function on the column blinds the filter.

full scan · to_char
where to_char(transaction_ts, 'YYYY-MM')
    = to_char(dateadd('month', -1, current_date()), 'YYYY-MM')
range on the raw column · prunes ~94%
where transaction_date >= date_trunc('month', …)
  and transaction_date <  date_trunc('month', current_date())

SELECT *

Columnar storage reads the columns you name. reference_no is 16 random characters, the expensive one.

UNION

UNION means UNION ALL plus a DISTINCT. Two different days cannot overlap, so the distinct is waste.

DISTINCT as a bandage

Duplicates came from a join. DISTINCT hides the bug and sorts the whole result. EXISTS asks the real question.

03_spilling_and_warehouse_size.sql

Rewrite first. Resize second.

XS · global window · perflab_03_xs_spill

ORDER BY with no PARTITION BY. One giant sort. Minutes, gigabytes spilled.

Same XS · partition + last 30 days

Prunes 95% of partitions. Seconds. Little or no spill. Same business answer.

Medium · same giant sort

Faster, less spill, still slow. A global ORDER BY cannot be split across nodes.

The bill

XS is 1 credit an hour. Medium is 4. If Medium finishes in under a quarter of the XS time, it costs less.

Billing is per second, 60 second minimum. Pruning is partitions you never open. Spill is memory after the rows are already here.

08_dbt_incremental_vs_full_refresh.md

Rebuilding every tick burns the day.

full refresh · the trap
48.2 s

The lab's printed line: CREATE TABLE AS. Every row, every five minutes, and the gap grows each day.

→
incremental · MERGE
3.1 s

The lab's printed line. Only rows inside the lookback window. The claim to prove: 20–100×.

Wrong filter

Filter on _extracted_at, not transaction_ts. A PENDING to POSTED update keeps the old timestamp and would be missed.

Lookback is 2 hours

Set it to 48 and the MERGE touches more rows. Set it to 0 and a batch that lands while dbt is reading can be skipped.

Full refresh has a place

After a logic fix. From the daily DAG. On a bigger warehouse. Once. Not every five minutes.

$dbt run --select fct_transactions --target prod
09_warehouse_sizing_and_concurrency.sql

A queue wants more counters.

One XS

20 dashboard queries. Each waits. queued_overload_time is the proof.

Three clusters

MAX_CLUSTER_COUNT 3. STANDARD starts one as soon as a query queues. Same size, so each query is not faster. The queue collapses.

One Medium

Each query is faster. The queue comes back once more than 8 run at once. ECONOMY waits about 6 minutes before it adds a cluster.

Scale up: a bigger warehouse, one heavy query, lab 03. Scale out: more clusters for a queue, this file.
